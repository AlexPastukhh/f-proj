# P5 — контракт дополнительных языковых адаптеров (проект, D-079)

Статус: **спецификация для следующего этапа, НЕ реализация адаптера**.
Подтверждённая пара сегодня: TypeScript/JavaScript + Vitest 5
(`vitest-5`) и C# + xUnit v3 (`xunit-v3`). Новые языки, в том
числе Python/pytest, в исходниках пока не поддерживаются.

## Семантический контракт, который нельзя менять

Семантический ключ склейки: `featureSpaceId + logicalFolderKey +
featureName + outcome + situation`. `partRole` обозначает
Frontend/Backend, а не язык. Дерево Testing и оба Projection
(Markdown/HTML) строятся из `JoinedSituation`, а не из
условий по синтаксису конкретного языка.

Каждый новый источник обязан предоставлять `TestDefinition[]`
(статическое определение), при необходимости
`FrameworkConcreteCase[]` (нативный тест-кейс), а все
неполные/недостоверные результаты — как `Diagnostic[]`
с явным `projectionImpact`. Типы расположены в
`src/core/types.ts` и уже используются в
`src/core/fullEngine.ts` / `src/core/projection.ts`.
Ни один адаптер не может синтезировать Situation из
текста ошибки или случайных бизнес-полей.

## Обязательное разделение фаз

1. **Статическое извлечение.** Код адаптера читает только
   разрешённый исходный root. Возвращает точные `SourceRange`,
   `definitionRef`, `assertions` и диагностику. Никаких
   выдуманных координат для динамических параметризованных данных.
2. **Нативная материализация.** Только в доверенном Workspace
   и только по явно настроенному проекту/окружению. Вернуть
   `frameworkCaseId`, точный `displayName`, обязательный
   `definitionRef` (включая frameworkProject). Значение Situation
   извлекать исключительно из подтверждённого case-label.
3. **Проекция.** Центральные `expandDefinitions`, `joinParts`
   и `buildProjectionDocument` не должны знать, какой язык
   создал исходный `TestDefinition`.
4. **Выполнение (отдельная capability).** Запуск возможен лишь
   при нативном доказательстве **ровно одного** выбранного теста,
   с повторным наблюдением входов, сохранением границ доверия,
   `AbortSignal` и fail-closed поведением. Анализ и Preview
   сами никогда не запускают пользовательские тесты.

## Объявляемые возможности вместо предположений

| Capability | Что обязан доказать новый адаптер |
| --- | --- |
| staticDefinitions | Точная привязка определения и assertions к исходнику |
| concreteCases | Native ID и подтверждённая Situation для каждой строки |
| navigation | Exact row при наличии доказательства, иначе definition |
| exactRun | Уникальный run target *до* исполнения, один executed case |
| cancellation | Остановка запущенных процессов и запрет ложного Passed |
| trustAndScope | Замкнутый workspace/project, отсутствие untrusted materialization |
| diagnostics | Явное degrade/block, никаких молчаливых частичных совпадений |

Отсутствующая capability **не подменяется** приблизительной
реализацией: например, при отсутствии native individual case ID
отключается только точный Run, но не весь Projection.

## Ближайшие решения P5

Первый *кандидат* — Python/pytest, затем Java/JUnit.
Приоритет не утверждён пользователем. Первый P5 шаг:
исследовательский pytest fixture с 1 прямым тестом,
2 параметризованными именованными кейсами и одним
недостоверным/дублирующимся кейсом; отдельно доказать
извлечение статического определения, нативный case ID и
безопасный отказ. Только после этого расширять union
`FeatureSourceConfig.adapter`, валидатор конфигурации,
`fullEngine`, паковку runtime и Testing API.
Никакого предположения, что названия/метки pytest совпадают
с Vitest/xUnit без явного контракта.

**Приёмка**: независимый Windows CI, fail-closed fixture,
повторяемая семантическая склейка без изменения текущей пары,
затем отдельная ручная проверка — не автоматически вместе
с релизом текущего MVP.
